# 04 — Live Tracking Design

**TOM Driver App** · v0.1 · 2026-06-26

---

## 1. Goal

Stream each on-duty driver's position to TOM accurately enough to make the **ops board** and
**customer ETAs** truthful, while staying battery- and data-frugal and legally consent-clean.
This is the capability that turns TOM's currently-placeholder map/ETA truthfulness (a flagged risk
in the commercial readiness plan) into honest data.

## 2. Capture strategy (on device)

### 2.1 Adaptive sampling
Fixed-interval GPS is the classic battery killer. We sample **adaptively by motion and context**:

| Context | Sample rate | Rationale |
|---------|-------------|-----------|
| Off duty | off | No tracking when not working (consent + battery). |
| On duty, no active job | every 60–120 s, low accuracy | Coarse availability/area only. |
| Active job, driving | every 10–20 s OR every ~100 m moved | Smooth board movement + ETA. |
| Approaching stop (inside geofence radius) | every 5 s, high accuracy | Precise arrival detection. |
| Stationary > 3 min | back off to 60 s | Don't drain battery at a kerb. |

Implementation: distance-filter + significant-change + activity recognition
(`react-native-background-geolocation` handles all three natively; Expo `expo-location` +
`expo-task-manager` is the licence-free fallback with coarser control).

### 2.2 Geofencing
On accepting a job, the app registers **geofences** around the pickup and each drop (radius
~120 m urban, larger rural). Entering a geofence:
- bumps sampling to high-accuracy,
- auto-prompts the matching status (**Arrived**) — driver confirms, never silently auto-transitions,
- starts the "dwell" timer that can feed waiting-time charges (`waiting_minutes`).
Exiting the final drop's geofence after POD can auto-suggest **COMPLETED**.

### 2.3 Battery & data discipline
- Batch pings (default 10) and flush on a timer/threshold; compress (delta-encode lat/lng).
- Use OS-efficient APIs (significant-location-change / fused location) when stationary.
- Respect Low Power Mode: widen intervals, warn ops the driver is in degraded tracking.
- Target: **< 35% incremental battery over a 9-hour shift** (success metric, Doc 01).

## 3. Transport & ingest (server)

### 3.1 Endpoint
`POST /api/driver/v1/location/batch` → `202 Accepted` (Doc 03 §7). **Best-effort and lossy by
design** — a dropped ping is fine; a dropped *business event* (scan/POD) is never acceptable, so the
two queues are separate (Doc 08): location uses a bounded ring buffer, events use a durable outbox.

### 3.2 Storage — new `driver_locations` table
Ships in both `database/schema.py` and `database/pg_schema.py`.

| Column | Type | Notes |
|--------|------|-------|
| `id` | INTEGER PK / SERIAL | |
| `driver_id` | TEXT | FK drivers |
| `device_id` | TEXT | binding |
| `recorded_at` | TEXT (ISO-Z) | device timestamp |
| `received_at` | TEXT (ISO-Z) | server timestamp |
| `lat`, `lng` | REAL | position |
| `speed`, `heading`, `accuracy_m` | REAL | motion/quality |
| `docket_number` | TEXT NULL | active job at time of ping |
| `battery_pct` | INTEGER NULL | telemetry |
| `is_moving` | INTEGER | 0/1 |

Indexes: `(driver_id, recorded_at)`, `(docket_number, recorded_at)`.
**PgBouncer-safe:** each batch is one multi-row `INSERT`, immediate commit, no open transaction held.

### 3.3 "Latest position" hot read
A lightweight `driver_latest_location` projection (one row per driver, upserted on ingest) gives the
board an O(1) read without scanning history. The spine reads this to enrich the board, so a
controller sees every active driver move in near-real-time.

### 3.4 Retention
Raw pings retained short (e.g. 30–90 days) for dispute/ops replay, then **down-sampled** to a
per-job breadcrumb (kept with the job for proof) and purged. Retention window is a configurable
policy and a GDPR data-minimisation control (Doc 09).

## 4. Surfacing the data

### 4.1 Ops board (v1)
- Live driver pins on the controller map; colour by status (idle/en-route/at-stop/late).
- Per-job ETA recomputed from current position via Google Distance Matrix (Doc 06), compared to
  `deadline_minutes` → drives the existing late/risk operational signals (`modules/tom/signal_layer.py`).
- Breadcrumb trail per job for after-the-fact proof of route taken.

### 4.2 Customer tracking (P1, behind product sign-off)
A tokenised, time-boxed public link (`/track/<opaque-token>`) showing the parcel's driver
approaching, with a coarse ETA — *not* the driver's identity or continuous history. Generated by
ops/booking, expires on delivery. Kept out of v1 default scope pending the consent/legal decision in
Doc 01 §8.

## 5. Consent & legality (must-haves, expanded in Doc 09)
- **Explicit, revocable consent** captured in-app before any background tracking; recorded with
  timestamp in `driver_actions`.
- **Only while on duty / on an active job** — never off-shift. The toggle is honoured and logged.
- Clear in-app indicator that tracking is active; OS-level "always allow location" justification
  string written for App Store / Play review.
- Subcontractors: tracking scope may differ by contract — make it a per-driver policy, not hardcoded.
- Data-minimisation + retention limits + driver's right to see/erase their own location data.

## 6. Failure modes & resilience
| Failure | Behaviour |
|---------|-----------|
| No signal | Pings buffer locally (ring buffer, capped), flush on reconnect; board shows "last seen" + greys the pin. |
| GPS denied mid-shift | App warns driver + notifies ops (tracking degraded); job work continues. |
| Device battery dies | Board shows last position + timestamp; no false "arrived". |
| Clock skew | Server records both `recorded_at` (device) and `received_at`; ETAs use server time. |
| Spoofing risk | Flag improbable jumps (speed/accuracy sanity checks) for ops; don't trust a single ping for billing. |

## 7. What "good" looks like
A controller opens the board and sees every on-duty driver moving smoothly, each active job carrying
a live ETA within ~8 minutes of reality; when a driver enters a delivery street the pin tightens and
the app prompts them to confirm arrival; when they finish, tracking for that leg ends automatically.
No driver is tracked off-shift, and no scan or POD is ever lost even where the pings were.
